# 内容数据中心第一版：功能与可能的实现

版本：讨论稿 v0.1 · 2026-09-11

本文供产品范围讨论和开发拆解使用。已确定的范围来自本次对话；字段、排序规则、采集策略、数据表和工具名称均为建议，尚未作为最终开发规格确认。本轮没有核实 JustOneAPI 的接口文档、套餐或返回样本，因此不承诺它具备下述全部能力。

配套文档：[千瓜页面学习与理解](./qian-gua-study.md)。竞品提供某项能力，不等于本项目已经具备相同的数据来源。

## 1. 第一版要做成什么

建设一个每天定时收集小红书笔记的数据中心，让用户查询已经收集的笔记，发现样本中热门和增长较快的关键词，查看热门笔记；同一套数据最终可以通过 MCP 查询。

用户打开页面、执行搜索或调用 MCP 时，查询本地已入库数据。外部接口调用由采集任务负责。

### 已确定的范围

```text
趋势
├── 热门关键词
└── 增长关键词

笔记
├── 笔记搜索
└── 热门笔记
```

- 第一版暂不做首页。
- 每天定时采集，并逐日积累数据，不要求上线时就拥有过去的历史数据。
- 暂不做达人相关功能、项目/投放管理、用户侧数据检测或监控、数据导出。
- 不使用 AI 批量分析或分类，不要求人工逐篇给笔记分类。
- 保持页面与流程简单，后续通过 MCP 暴露数据。

采集任务必要的成功/失败日志属于内部运行保障，不设计成用户侧“数据监控”产品。

### 建议的产品边界

第一版只宣称展示“本数据中心已采集样本”的表现，不宣称全小红书热度、真实搜索量或全行业覆盖。

品牌分析、品类大盘、评论分析、用户画像、预估曝光阅读、商业投放识别、相似笔记等暂不加入。可以保存接口合法提供且有用的基础字段，但不因此增加页面。

## 2. 四个页面怎么用

### 2.1 热门关键词

**用户问题**：最近采集到的内容里，哪些主题出现得多，有哪些笔记可以参考？

建议第一版把可稳定提取的原始话题标签作为关键词来源。对外显示“来源：笔记话题标签”，避免让用户以为这是搜索引擎热搜词。

| 项目 | 建议 |
|---|---|
| 时间 | 近 7 天、近 30 天，使用截至最近完整采集日的连续自然日窗口 |
| 结果列 | 关键词、关联笔记数、已观测互动量、数据截至时间 |
| 默认排序 | 关联笔记数降序，互动量作为同分次序 |
| 点击关键词 | 进入笔记搜索，带入关键词、对应样本时间条件和结果批次 |
| 空结果 | 显示尚未积累到符合条件的样本，不显示虚构榜单 |

关联笔记数按笔记 ID 去重。同一篇笔记重复出现同一个标签，只贡献一次计数。

### 2.2 增长关键词

**用户问题**：在相同采集规则下，哪些主题比上一周期出现得更多？

| 项目 | 建议 |
|---|---|
| 比较周期 | 最近连续 7 个自然日与之前连续 7 个自然日，两个窗口均须完整采集 |
| 结果列 | 关键词、本期笔记数、上期笔记数、增加篇数、增长率/新增标记 |
| 默认排序 | 增加篇数降序，不单纯按百分比排序 |
| 点击关键词 | 查看对应结果批次的本期关联笔记，并保留与上期对照的时间入口 |
| 不足 14 日 | 提示比较数据积累中，可继续使用热门关键词 |

第一版只计算笔记数量增长，不同时增加互动增长榜、热度预测等功能。

### 2.3 笔记搜索

**用户问题**：在已经采集的笔记中，查找某个主题及其具体内容。

建议提供搜索框、时间范围、图文/视频筛选，以及最新收录/互动量/点赞/收藏排序。先不做复杂高级检索。

搜索框默认匹配已存储的标题、正文和话题标签；正文缺失时不声称能搜索全文。由关键词榜进入时，使用该结果批次的精确关键词关联筛选，避免变成模糊文本搜索或最新关联后出现不同数量。普通搜索默认使用最新可用数据；榜单下钻明确显示所用批次。

结果展示标题、封面（若有）、发布时间、首次采集时间、点赞、收藏、评论、互动量、最近成功采集时间。作者名称可作为原文署名保留，不建设达人主页或达人分析。

点击结果打开一个简单的笔记详情面板：已有正文、标签、基础计数、原文链接和数据时间。它是笔记模块的下钻内容，不增加一级导航。

### 2.4 热门笔记

**用户问题**：在近期收录的样本中，哪些笔记当前互动表现较高？

建议提供近 7 天/近 30 天、图文/视频、关键词筛选；按已观测互动量降序，支持切换点赞或收藏排序。行内字段和详情面板复用笔记搜索。

这里的“热门”指样本内累计表现，第一版不承诺近期互动增速或全平台排行。不使用尚未确定门槛的“爆文”标签，也不复制千瓜的预估阅读数。

## 3. 不用 AI，关键词如何产生

### 建议先不建设完整行业分类体系

我们当前四个页面依赖关键词与笔记的关联，并不必然需要把每篇笔记分到“美妆、母婴、家居”等行业。

推荐流程：

```text
原始笔记
  → 读取接口的结构化话题标签
  → 如果没有结构化标签，尝试从已有正文提取明确的 #话题
  → 规范化和去重
  → 保存“笔记—关键词”关联
  → 每日统计
```

这里的正文提取需要根据真实样本确定边界规则；没有可靠标签或正文时，保留笔记但不编造关键词。

第一版规范化只处理前后空白、明显的标签包裹符号及一致的字符格式。保留原始标签。不同词不自动视为同义词，例如“防晒”“防晒霜”“防晒衣”先分别统计。

可以配置少量通用无意义标签排除规则；这是全局规则维护，不是人工逐篇分类。规则变化应记录版本，避免无声改变历史榜单口径。

如果以后要增加行业筛选，再单独讨论接口现成分类或词典匹配。不要在第一版同时引入完整行业词库、分词发现、同义词归并和语义聚类。

## 4. 每天采集什么

### 4.1 先有可控的采集范围

“每天采集”仍需要一个起点。建议第一版以少量配置好的种子关键词作为采集入口，前提是 JustOneAPI 确实提供相应的笔记检索能力。

这些种子词决定我们能观察哪些内容，不是对全平台的无偏抽样。第一版不做用户自助配置复杂采集任务的后台；可以由部署配置维护范围与每日预算。

区分两个概念：**种子关键词用于发现笔记，笔记自身的话题标签用于产生榜单关键词。** 二者分别保存，不把采集时的搜索词直接冒充笔记标签。

### 4.2 每日任务建议

1. 按配置的种子词调用发现接口，在分页上限和调用预算内取得候选笔记。
2. 按稳定笔记 ID 去重；同一篇从多个入口发现只入库一次，并保留多个来源关联。
3. 如果发现接口缺少所需字段，而且确有详情接口，再按预算补充详情。
4. 为近期笔记补采基础计数；优先覆盖近期新收录笔记，其次覆盖候选热门笔记。采用固定且记录在案的规则。
5. 提取可靠话题标签，保存来源数据时间和本次抓取时间。
6. 生成当日汇总，完成检查后发布本批榜单数据。

建议每日固定时刻运行，使用 Asia/Shanghai 的自然日作为产品统计日。具体时刻在确定接口更新节奏和额度后再配置。

这里的补采是内部更新策略，不是用户侧“监控某条笔记”的功能。

### 4.3 失败与成本

单条请求失败不能把旧计数覆盖成零。可重试的失败有限次数重试，任务保留失败原因；限流遵循服务方实际规则。

同一批次可恢复执行，重复运行不增加笔记数量。对未达既定完整度标准的批次，不替换最近完整榜单；页面展示上一个成功批次和延迟状态。

调用量主要由三部分构成：发现请求、详情补充请求、已有笔记刷新请求。每一部分设每日上限。接口单价、分页大小及计费方式未确认，因此这里不给出虚构金额或覆盖规模。

## 5. 统计口径建议

### 5.1 第一版统一采用“首次采集日”确定样本窗口

这是为了让每日积累的数据形成可解释的窗口，并不代表最近发布的全平台内容。

- 笔记的发布时间用于展示；首次采集时间用于默认时间筛选和榜单样本归属。
- 热门关键词、增长关键词、热门笔记默认都按首次采集日圈定样本。
- 用户可见的时间筛选明确标为“收录时间”；不要只写一个含义不清的“时间”。

如果未来改成按发布时间统计，应重新命名、记录口径版本，并处理迟到收录；不要在同一榜单中混用两个口径。

### 5.2 关键词数量与增长

设最后一个完整采集日为 T：

```text
本期：T-6 到 T，共 7 天
上期：T-13 到 T-7，共 7 天

本期笔记数 = 本期首次采集、关联该关键词的不同笔记 ID 数
增加篇数 = 本期笔记数 - 上期笔记数
增长率 = 增加篇数 / 上期笔记数 × 100%（仅当上期 > 0）
```

上期为零而本期有数据，标为“新增”，不显示无限增长。可以设置一个本期最低样本量门槛，例如 5 篇，作为可调整的降噪参数；这是建议值，不是已定需求。

窗口始终由连续自然日构成，不跳过失败日再向前凑足天数。两个周期必须采用相同采集范围和相近执行完整度。种子词或分页预算显著变化、采集日缺失时，该比较应标记不可比；范围变化后可等待两个完整可比周期再恢复增长排名。

第一天初始化可能收录大量旧笔记。因此增长榜还应排除初始化批次，至少等 14 个采用日常采集规则的完整采集日；不能把初始化量与日常新增直接比较。

### 5.3 互动量与快照

第一版建议统一采用点赞 + 收藏 + 评论作为互动量，三个原始字段都要保存。分享可在接口可用时另存，但不默认加入这一口径。

关键计数缺失时，互动量为不可计算，而不是把缺失当零。该笔记仍能被搜索，也可以贡献关键词笔记数，但不参与依赖完整互动量的排序。界面显示缺失状态。

榜单中的互动是截至本批所掌握的累计计数，**不是这些互动都发生在所选 7 天或 30 天内**。每篇笔记的最近成功采集时刻可能不同，因此行内要显示更新时间。

第一版关键词互动汇总仅加总有完整计数的关联笔记，并同时返回计数覆盖数/关联笔记总数，避免部分采集看起来像完整汇总。不同关键词共享笔记，因此不能把多个关键词互动量相加当作全库互动量。

每日快照从首次采集开始保存，不倒推出更早历史。本版不开放互动增量排行；后续需要两个实际观测点才能讨论增量，并处理计数回落。

## 6. 一个保持简单的实现结构

这是逻辑方案，不指定尚未核实的框架版本、数据库扩展或部署产品。

```text
JustOneAPI
    ↓ 定时采集、去重、必要的详情补充
笔记与每日观测数据
    ↓ 关键词关联、批次统计
统一查询服务
    ├── Web 页面
    └── 只读 MCP 工具
```

建议一个后端应用、一套数据库、一个定时采集执行入口。第一版不因未来规模预先拆成微服务，也不先建设独立搜索集群。数据库的简单文本检索能力能满足初期规模时先复用；真实数据量和搜索质量不足时再评估升级。

### 最小数据结构

| 数据 | 关键内容 |
|---|---|
| 笔记 | 平台笔记 ID、标题、正文、形式、原文链接、封面、原始话题、发布时间、首次采集时间、最近成功采集时间 |
| 笔记每日观测 | 笔记 ID、统计日、点赞/收藏/评论/分享、实际采集时刻、缺失状态 |
| 关键词与关联 | 规范词、原词、提取规则版本、笔记 ID；同一笔记同一词唯一 |
| 采集来源关联 | 笔记 ID、种子词或入口、首次发现批次 |
| 采集批次 | 范围版本、计划与成功任务、请求量、失败记录、完整度、发布日期 |
| 榜单汇总 | 榜期、范围/规则版本、关联笔记数、互动汇总及覆盖数、所用批次 |

上表是逻辑对象，不要求必须分别建成六张表。每日观测按“笔记 ID + 统计日”去重，同日重试选择最近成功观测；保留实际观测时刻，不用任务结束时间冒充源数据时间。

一个已发布榜期需要绑定结果批次，同时固定关键词关联的笔记成员集合与用于统计的观测快照，后续补采或标签变化不静默改变已发布数值。榜单下钻使用同一批次的成员集合与计数；详情如果展示更新的计数，需另外标明更新时间。若重算则产生新版本，页面与 MCP 都能说明使用了哪一版。

## 7. MCP 如何暴露

MCP 与网页复用同一查询服务，不各自计算热度、筛选条件和增长率。调用 MCP 默认不触发新的 JustOneAPI 采集。

建议第一版提供五个只读工具，名称为提案：

| 工具 | 用途 | 主要参数 |
|---|---|---|
| `search_notes` | 搜索已采集笔记 | 文本或关键词、收录区间、内容形式、排序、分页、可选结果批次 |
| `get_note` | 读取单篇详情 | 笔记 ID |
| `get_hot_notes` | 读取热门笔记 | 窗口、关键词、排序、分页 |
| `get_hot_keywords` | 读取热门关键词 | 窗口、分页 |
| `get_growing_keywords` | 读取增长关键词 | 比较周期、最小样本量、分页 |

返回结果除了数据，还需带上：统计窗口、时间字段含义、数据截至时间、采集范围版本、口径版本、结果批次、覆盖或不完整状态、下一页标识。榜单下钻须传回结果批次；分页也绑定该批次，避免翻页时结果漂移。

工具描述应明确“采集样本”“累计互动”“首次收录窗口”等含义，让调用方能够准确转述。第一页、分页上限与返回字段固定，避免一次返回全库正文。

接口错误和业务空结果分开：没有匹配笔记是正常空列表；增长数据尚未积累够属于未就绪状态；查询失败是错误。缺失值保留为空值及原因。

对外可访问的 MCP 入口需要身份校验和数据访问范围控制。具体连接方式、认证实现与客户端兼容性，留到确定部署方式后依据官方 MCP 规范确认；本稿不指定未经验证的协议实现细节。

## 8. 开发前先核实 JustOneAPI

以下均是能力核对项，不是已经确认存在的接口名称。

| 待核实能力 | 为什么需要 | 不满足时的影响 |
|---|---|---|
| 按词发现笔记、分页与排序能力 | 每日稳定获得样本 | 必须改为其他已提供的发现入口，不能承诺预设采集方式 |
| 稳定笔记 ID | 去重与连续观测 | 无可靠标识则无法可靠统计，应先解决 |
| 标题、正文、原始话题标签 | 搜索与关键词关联 | 缺正文则不做全文搜索；缺可靠标签则关键词方案需调整 |
| 发布时间、链接、内容形式 | 内容呈现 | 缺失字段按不可用处理，不推断填充 |
| 点赞、收藏、评论等计数 | 热门笔记及互动汇总 | 缺关键计数则收缩或调整排序口径 |
| 详情查询与已有笔记重查能力 | 补充字段和刷新快照 | 不可刷新时只展示首次观测数据，不能承诺持续更新 |
| 时间筛选、结果截断和检索覆盖 | 评估周期可比性 | 只能标注受限样本，不能假设搜索返回全量 |
| 配额、限流、失败计费规则 | 设定每日调用上限 | 未确认前不承诺规模与成本 |
| 数据保存和向下游提供的使用条件 | 确认长期入库与 MCP 的允许范围 | 按实际允许范围调整字段和暴露方式 |

实施前应取得少量真实响应，验证字段缺失、标签格式、重复结果、计数类型和更新行为。本稿不需要 API 密钥，也不包含密钥。

## 9. 建议实施顺序与验收

### 第一步：跑通小范围真实采集

核对接口与字段，确定少量种子词和请求上限；完成笔记去重、来源关联与快照。验证重复运行不会增加笔记总数，失败不会覆盖已有有效数据。

### 第二步：完成笔记搜索与简单详情

先让数据可查。验证用户搜索只查本地；时间筛选含义明确；缺失字段可识别；从结果可打开已有详情及原文。

### 第三步：上线热门笔记与热门关键词

复用采集数据和查询服务，完成话题提取与统计。人工抽样核对计算结果即可，不开展人工逐篇分类。验证重复标签和多入口发现不会重复计数，关键词下钻与榜单样本一致。

### 第四步：具备可比周期后开放增长关键词

开发可先完成，真实榜单等待足够数据。验证上期零值、初始化批次、缺采日、范围变化和小样本等情况；不可比时不输出误导性的增长名次。

### 第五步：接入只读 MCP

复用前四步查询服务。验证相同参数与结果批次下 MCP 和网页统计一致，分页有上限，调用不会触发外部采集；同时验证空结果、未就绪和错误状态。

第一版完成标准是这四类查询可以基于每日积累的数据稳定使用，并能被 MCP 以一致口径读取。不是复刻千瓜所有页面，也不是生成规模庞大的行业分类体系。

## 10. 本稿仍待确定的少数决策

- JustOneAPI 实际可用的发现、详情和刷新能力。
- 第一批采集主题、每日调用预算与可接受的数据滞后。
- 是否接受“原始话题标签作为第一版关键词来源”。
- 是否接受“首次采集日作为默认榜单时间口径”。
- 试用用户与 MCP 的部署、访问方式。

上述待定项不妨碍讨论四页产品结构，但其中接口能力与采集范围应在正式开发前落实。所有建议值可在拿到真实样本后调整。
