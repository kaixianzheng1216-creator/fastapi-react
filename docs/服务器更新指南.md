# 服务器更新指南

适用于服务器当前为 `e8783edd`、准备更新到 `7666cb64` 的情况。这次更新把账号密码登录改为钉钉登录，并迁移用户表；**不能只拉取代码并重启**。以下命令在 Linux 服务器的项目根目录执行。先用 `cd` 进入服务器上的 `fastapi-react` 目录；每组命令在同一个终端中按顺序运行，遇到错误先停下。

所有 `docker compose` 命令都指定 `-f compose.yml`，表示只使用正式部署配置，避免自动加载开发用的 `compose.override.yml`。

## 本次更新：切换到钉钉登录

1. 确认版本，备份数据库和现有配置：

   ```bash
   git rev-parse --short HEAD
   backup="$HOME/fastapi-react-before-auth-$(date +%Y%m%d-%H%M).dump"
   docker compose -f compose.yml exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup"
   test -s "$backup" && echo "数据库备份：$backup"
   cp -p .env "$HOME/fastapi-react.env.before-auth"
   ```

   - `git rev-parse --short HEAD` 显示服务器当前提交，应为 `e8783edd`；若不同，先核对实际版本。
   - `backup=...` 把备份文件名存入当前终端的变量；时间戳避免覆盖旧备份。
   - `docker compose ... exec -T db ... pg_dump ... -Fc` 在正在运行的 PostgreSQL 容器中导出数据库。`-T` 关闭交互终端，`-Fc` 生成便于恢复的自定义格式备份，`> "$backup"` 将结果保存在服务器主机上。
   - `test -s "$backup"` 检查备份文件非空；检查失败就不要迁移。`cp -p .env ...` 另存当前环境配置并保留文件权限。

2. 准备登录配置。请统一认证服务负责人将 `https://你的域名/login` 加入生产回跳地址白名单。用 `nano .env`（或服务器上已有的编辑器）打开项目根目录的配置文件，新增或修改下列值；原有数据库密码及其他服务密钥保持不变：

   ```dotenv
   ENVIRONMENT=production
   APP_ORIGIN=https://你的域名
   BACKEND_CORS_ORIGINS=https://你的域名
   AUTH_SERVER_URL=https://生产统一认证服务地址
   AUTH_SERVICE_TOKEN=生产环境的服务令牌
   ```

   把示例中的域名、认证服务地址和令牌换成真实值，不要原样复制。`APP_ORIGIN` 是浏览器访问的 HTTPS 来源，只写协议和域名（非标准端口还需包含端口），不加 `/login`；应用会用它生成钉钉回跳地址。`BACKEND_CORS_ORIGINS` 填同一来源。`ENVIRONMENT=production` 会启用安全 Cookie，并要求认证服务及应用地址都使用 HTTPS。管理员绑定还需要事先核实其**生产环境统一用户 ID**，不要照搬测试文档里的 `41`。

3. 等正在处理的任务结束后，更新并迁移：

   ```bash
   git fetch origin master
   git merge --ff-only 7666cb64
   docker compose -f compose.yml config --quiet
   docker compose -f compose.yml build
   docker compose -f compose.yml stop frontend backend agent-worker knowledge-worker
   docker compose -f compose.yml run --rm --no-deps prestart
   docker compose -f compose.yml run --rm --no-deps backend python -m scripts.bind_auth_admin --username admin --auth-user-id "已核实的生产统一用户ID"
   docker compose -f compose.yml up -d --no-deps backend agent-worker knowledge-worker frontend
   ```

   - `git fetch origin master` 下载远端提交，但暂不改变当前运行的代码；`git merge --ff-only 7666cb64` 将服务器代码快进到本次指定版本。如果不能快进，命令会停止，不要强制合并。
   - `docker compose ... config --quiet` 检查 Compose 文件和必需环境变量能否解析；无输出且退出码为 0 才继续。
   - `docker compose ... build` 提前构建新镜像。构建失败时旧容器仍在运行，因此把它放在停服务之前。
   - `docker compose ... stop ...` 停止旧前后端及两个 Worker，避免数据库结构变更时仍有旧代码读写。先等队列中的任务结束。
   - `docker compose ... run --rm --no-deps prestart` 启动一次性迁移容器；它会执行 `alembic upgrade head`。本次迁移添加统一身份字段，并删除旧密码字段。命令成功结束后才继续。
   - `docker compose ... run --rm --no-deps backend python -m scripts.bind_auth_admin ...` 将本地 `admin` 绑定到已核实的生产统一用户 ID，保留原管理员的数据和权限。`--rm` 运行后删除临时容器，`--no-deps` 不重复启动数据库等依赖。若绑定失败，不要启动新服务。
   - `docker compose ... up -d --no-deps ...` 用已构建的镜像重新启动业务容器；`-d` 表示后台运行。这里假定原有数据库、Redis 和 Qdrant 仍在运行。

4. 检查容器和登录：

   ```bash
   docker compose -f compose.yml ps
   curl -fsS http://127.0.0.1:3001/api/v1/utils/health-check/
   ```

   `docker compose ... ps` 用来查看容器是否运行以及后端健康状态。`curl -fsS` 从服务器本机访问前端端口，经前端代理检查后端接口；非成功状态会报错。如果失败，再查看 `docker compose -f compose.yml logs --tail=100 backend frontend`。

   再通过正式 HTTPS 域名打开 `/login`，验证钉钉登录及管理员权限。如果迁移或绑定失败，先排查错误，不要继续启动业务服务。迁移会删除旧密码字段；回退旧版本需要恢复数据库备份。详细背景见[用户体系接入指南](./用户体系-接入指南.md)。

## 以后只更新前端页面

已经完成上述一次性迁移后，若变更仅涉及前端，可以执行：

```bash
git pull --ff-only origin master
docker compose -f compose.yml up -d --build --no-deps frontend
```

`git pull --ff-only origin master` 拉取并快进代码；`up -d --build --no-deps frontend` 只重建并启动前端容器，不重新启动后端及数据库。只有确认本次变更仅涉及前端时才这样做；涉及后端、Worker 或数据库的更新，应先查看对应变更和迁移说明。
