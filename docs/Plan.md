# 小红书内容研究：下一阶段工作计划

讨论稿 · 2026-09-11

## 我们要做什么

围绕小红书的选题研究和内容参考，在现有「数据中台」后台中建设每日更新的小红书内容库。基于 JustOneAPI 定时采集笔记，帮助使用者查找相关内容、比较互动表现，并逐步观察话题变化。

第一阶段重点回答三个问题：**某个主题有哪些笔记值得参考？这些笔记的点赞、收藏、评论表现如何？在我们持续采集的样本里，哪些话题开始增多？**

例如，使用者研究“亲子露营”时，可以查找已收录的小红书笔记，按收藏或点赞筛选，打开具体内容作参考；在积累足够且可比的数据后，再观察相关话题的变化。这是预期使用场景，不代表已接入该主题的数据。

## 用户能获得什么

| 功能 | 要解决的问题 |
|---|---|
| 内容搜索 | 按主题查找已采集的小红书笔记，查看标题、已有文本、图片等信息 |
| 热门内容 | 在小红书采集样本中，筛选点赞、收藏、评论表现较高的笔记作参考 |
| 热门关键词 | 在数据来源和统计依据验证后，发现值得研究的小红书主题，并查看相关笔记 |
| 增长关键词 | 在可比采集周期内，观察哪些小红书主题的相关笔记样本增加 |

入口统一放在现有后台中：

```text
内容运营
├── 平台榜单（已有）
├── 内容搜索
├── 热门内容
├── 热门关键词
└── 增长关键词
```

内容详情、关键词详情从列表进入，不另占菜单。菜单统一沿用“内容”命名，本阶段实际建设和验收均聚焦小红书；已有“平台榜单”不计入本次新增业务。

## 当前进展

- 已完成千瓜可访问页面的学习，整理了功能结构与统计口径。
- 已加入四个后台菜单及统一的建设中页面，业务数据尚未接入。
- 已核对小红书搜索 V4 的文档和官方响应示例：可见内容标识、标题、文本、作者基础信息、图片和互动计数；尚未完成我们自己采集任务的实际验证。
- 示例中的文本存在截断迹象、标签为空，因此完整内容与关键词来源仍需核实，不能直接承诺话题分析可用。

接口依据：[JustOneAPI 搜索 V4 文档](https://docs.justoneapi.com/zh/api/xiaohongshu-rednote/note-search-v4)及其公开响应示例。

## 接下来按什么顺序做

### 1. 验证采集能力

选取少量小红书主题试采，核对笔记搜索与详情接口，确认文本、图片、话题标签和互动计数的可用程度，以及分页限制、重复率、刷新能力和调用成本。

**交付：真实样本、可用能力清单、建议采集范围和每日成本估算。**

### 2. 跑通每日采集与内容查询

完成小红书笔记的定时采集、去重入库、失败处理和计数快照，接入内容搜索、热门内容及共用内容详情。用户查询已有数据，外部采集由后台任务负责。

**交付：用户能在后台查到实际采集的内容、按指标排序，并看到数据更新时间；随采集积累表现记录。**

### 3. 验证并建设关键词业务

确认可靠的关键词来源，再建设关键词与内容的关联、相关内容查询和变化展示。优先使用接口提供的话题信息；不依赖 AI，也不逐篇人工分类。

热门和增长排名必须有可解释的依据。如果每个搜索词采集数量相同，不能把采集配额当热度；如果采集范围变化或周期缺采，不能把数据差异直接解释为增长。

**交付：经样本验证的关键词来源和统计规则，再开放相应页面。数据依据不足时，先交付内容模块。**

### 4. 接入现有 MCP

通过现有 MCP 入口，将小红书内容搜索和详情查询提供给其他应用或助手，关键词能力成熟后再扩展。复用后台查询能力，返回数据同时说明统计范围和更新时间。

**交付：后台与 MCP 对相同数据给出一致结果，不另建一套计算逻辑。**

## 第一阶段如何控制范围

复用现有后台、账号权限和 MCP 入口。暂不增加 AI 分析、人工分类流程、达人分析、项目管理、用户侧监控或数据导出。

先让小范围真实数据稳定流转，不提前承诺小红书全平台覆盖、关键词真实搜索量或历史数据回溯能力。数据库字段和具体实现单独讨论，不作为本次沟通重点。

抖音、快手等平台属于后续扩展，本阶段不同时推进。未来通过页面内的平台选择承接，复用现有功能入口。

**下一步先用一轮小范围采集确定能力、成本和交付边界，再据此排开发计划。**
