# 业务平台统一登录接入指南

## 1. 接入范围

统一 Auth Server 提供：

- 短信验证码登录；
- 钉钉企业员工登录；
- 统一用户 access token 和 refresh token。

推荐业务平台使用同源 BFF 接入。前端只请求业务平台自己的后端，
由 BFF 调用 Auth Server 并保存 Token。

Auth Server 地址：

| 环境 | 地址 |
|------|------|
| 测试 | `https://auth-test.gbotai.cn` |
| 生产 | `https://auth.middle.gbotai.cn` |

## 2. 接入准备

接入方需要向用户体系负责人提供：

| 信息 | 示例 |
|------|------|
| 平台标识 `platform` | `demo` |
| 测试回跳地址 | `http://localhost:8080/` |
| 生产回跳地址 | `https://demo.example.com/login` |

`platform` 只能包含小写字母、数字和连字符，长度不超过 20。

用户体系负责人需要在 Auth Server 环境中配置：

```env
AUTH_SUPPORTED_PLATFORMS=lingji,ai-knowledge,colly,demo
DINGTALK_RETURN_URLS=https://已有地址.example.com/login,http://localhost:8080/
```

说明：

- `AUTH_SUPPORTED_PLATFORMS` 支持多个平台，使用英文逗号分隔；
- `DINGTALK_RETURN_URLS` 支持多个完整地址，使用英文逗号分隔；
- 当前 `DINGTALK_RETURN_URLS` 地址列表对所有受支持平台生效；
- `return_url` 按完整字符串匹配，包括协议、端口、路径和末尾 `/`；
- 修改配置后必须重新部署或重启 Auth Server；
- 本地可以使用 HTTP，生产回跳地址必须使用 HTTPS。

## 3. 业务平台配置

业务平台 BFF 至少需要以下配置：

```env
AUTH_SERVER_URL=https://auth-test.gbotai.cn
AUTH_PLATFORM=demo
DINGTALK_RETURN_URL=http://localhost:8080/
```

`AUTH_PLATFORM` 和 `DINGTALK_RETURN_URL` 必须由服务端固定配置，
不能接受浏览器任意传入。

## 4. Auth Server 接口

| 功能 | 方法与接口 | 请求参数 |
|------|------------|----------|
| 发送短信验证码 | `POST /api/user/send-code` | `{"mobile":"13800000000"}` |
| 短信验证码登录 | `POST /api/user/login/captcha` | `{"mobile":"13800000000","code":"123456","platform":"demo"}` |
| 发起钉钉登录 | `GET /api/user/login/dingtalk/authorize` | Query：`platform`、`return_url` |
| 兑换钉钉 ticket | `POST /api/user/login/dingtalk/exchange` | `{"ticket":"..."}` |
| 退出登录 | `DELETE /api/user/logout` | Header：`Authorization: Bearer <access_token>` |

接口使用统一响应格式：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

`code=0` 表示成功，其他值为业务错误。

## 5. 短信登录流程

1. 前端将手机号提交给业务 BFF；
2. BFF 调用 Auth Server 的 `/api/user/send-code`；
3. 用户输入验证码后，前端将手机号和验证码提交给 BFF；
4. BFF 使用固定的 `platform` 调用 `/api/user/login/captcha`；
5. BFF 保存 Auth Server 返回的 Token，并建立业务登录态。

业务平台可以自行增加手机号格式校验和防刷限制，但登录资格最终由 Auth Server 判断。

## 6. 钉钉登录流程

1. 用户点击“钉钉登录”；
2. 浏览器访问业务 BFF 的钉钉登录入口；
3. BFF 使用固定配置拼接并跳转：

   ```text
   GET <AUTH_SERVER_URL>/api/user/login/dingtalk/authorize
       ?platform=<AUTH_PLATFORM>
       &return_url=<DINGTALK_RETURN_URL>
   ```

4. Auth Server 完成钉钉授权后跳回业务平台：

   ```text
   成功：<return_url>?ticket=<one_time_ticket>
   失败：<return_url>?error_code=<business_error_code>
   ```

5. 前端将 `ticket` 提交给业务 BFF；
6. BFF 调用 `/api/user/login/dingtalk/exchange` 兑换 Token；
7. BFF 保存 Token，并建立业务登录态。

`ticket` 默认 60 秒有效且只能成功兑换一次。前端必须：

- 防止组件重复执行导致重复兑换；
- 兑换完成后清除地址栏中的 `ticket` 和 `error_code`；
- 收到 `10021` 后重新发起登录，不要重复提交旧 ticket。

## 7. Token 与 Session

推荐由 BFF 保存 access token 和 refresh token，浏览器只持有业务 Session Cookie。

Cookie 建议设置：

- `HttpOnly`；
- `Secure`，生产环境必须启用；
- 合适的 `SameSite`；
- 明确的有效期。

禁止：

- 在 URL 中传递 access token 或 refresh token；
- 在前端持久化 refresh token；
- 在日志中记录完整 ticket 或 Token；
- Auth Server 不可用时绕过认证创建本地登录态。

后续业务接口可以使用以下任一方式验证 access token：

```http
GET /internal/token/verify
X-Service-Token: <service_token>
Authorization: Bearer <access_token>
```

或使用 Auth Server 提供的 JWKS 在本地验证 RS256 JWT。

`X-Service-Token` 只能保存在业务后端，不能发送到浏览器。

### 7.1 登录校验中间件

业务平台应为所有受保护接口统一接入认证中间件，不要在每个接口中重复判断登录状态。

中间件的基本流程：

1. 从 `HttpOnly` Cookie 中读取 Session ID；
2. 从 Redis、数据库或其他服务端存储查询 Session；
3. 检查 Session 和 access token 是否过期；
4. 校验失败返回 HTTP `401`；
5. 校验成功后把 `user_id` 等用户信息写入请求上下文，再执行后续业务逻辑。

`GET /api/me` 也应复用该中间件：校验成功返回当前用户，返回 `401`
表示未登录或登录已过期。前端不能通过本地变量或是否存在 Cookie 判断登录状态。

如果业务接口直接接收 Auth Server access token，中间件应使用 JWKS 本地验证 JWT，
或调用 `/internal/token/verify`。本地验证性能更好；调用内部接口可以获得更及时的
服务端校验结果，但会增加网络依赖。

## 8. Auth Server 校验范围

Auth Server 会校验：

- `platform` 是否已登记；
- `return_url` 是否在允许列表中；
- 短信验证码及请求频率；
- 钉钉 OAuth state；
- 钉钉组织和手机号；
- 本地账号状态；
- ticket 是否有效、过期或已使用。

当前登录和 ticket 兑换接口不要求 `X-Service-Token`，也没有使用 mTLS
校验业务 BFF 身份。

## 9. HTTPS 与容器证书

BFF 必须校验 Auth Server 的 HTTPS 证书，不能关闭 TLS 校验。

如果最终容器使用 `scratch` 等不包含 CA 根证书的镜像，需要将 CA 文件复制到最终镜像：

```dockerfile
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt
```

使用已包含 CA 证书的基础镜像时不需要额外处理。

## 10. 常用错误码

| code | 含义 | 建议处理 |
|------|------|----------|
| `10001` | platform、return_url 或提交参数不正确 | 检查平台和回跳地址配置 |
| `10002` | 验证码错误 | 提示用户重新输入 |
| `10005` | 本地账号已停用 | 联系管理员 |
| `10017` | 钉钉登录服务不可用 | 稍后重试 |
| `10018` | 选择了错误的钉钉组织 | 切换到本公司组织 |
| `10020` | OAuth state 无效或过期 | 重新发起钉钉登录 |
| `10021` | ticket 无效、过期或已使用 | 重新发起钉钉登录 |
| `10022` | 未获取到合法手机号 | 检查钉钉权限和手机号 |
| `10023` | 请求过于频繁 | 稍后重试 |
| `50001` | Auth Server 或网络异常 | 检查服务、网络和 HTTPS 证书 |

- [ ] BFF 固定了 `platform` 和 `return_url`；
- [ ] 短信发送和验证码登录正常；
- [ ] 钉钉登录能够跳转并正确回到业务平台；
- [ ] ticket 不会重复兑换；
- [ ] 受保护接口已统一接入登录校验中间件；
- [ ] 未登录或登录过期时接口返回 HTTP `401`；
- [ ] 浏览器和 URL 中不存在 Auth Server Token；
- [ ] 登录、刷新、退出和业务接口鉴权正常；
- [ ] 生产环境使用 HTTPS 和 `Secure` Cookie。


## 12. data-hub 项目实现与部署

本项目由 FastAPI 对接 Auth Server，Redis 保存登录 Session，浏览器仅保存
`data_hub_session` HttpOnly Cookie。PostgreSQL 保留用户 UUID、项目成员关系与业务权限。
普通用户首次登录自动建立本地身份映射，不授予项目或平台管理权限。

### 配置

后端仅配置 `AUTH_SERVER_URL`、`AUTH_SERVICE_TOKEN`、`APP_ORIGIN`。
本项目的平台标识固定为 `data-hub`，回跳地址由 `APP_ORIGIN + /login` 生成，
不再单独配置。前端服务配置相同的 `APP_ORIGIN`，用于流式代理
校验浏览器请求来源。密钥放在部署环境或未跟踪的 `.env` 中。

本地使用 `APP_ORIGIN=http://localhost:3001`，回跳地址为
`http://localhost:3001/login`。生产使用实际 HTTPS 域名，
并在 Auth Server 登记对应的完整 `/login` 回跳地址。反向代理必须保留 Cookie、Origin 和 Set-Cookie。
访问日志不得记录登录回跳 URL 的查询参数。

### 一次性迁移

先备份数据库，前后端在同一个维护窗口切换，停止旧密码登录服务。项目根目录执行：

```sh
uv run --directory backend alembic upgrade head
uv run --directory backend python -m scripts.bind_auth_admin --username admin --auth-user-id 41
```

本地从主机连接 Docker 数据库时，将 `POSTGRES_SERVER` 临时设为 `127.0.0.1`。
容器内保持 `db`。`41` 是本次实测的测试环境统一用户编号，生产环境必须独立确认。
脚本保留现有 admin 的 UUID、权限和数据；若是全新数据库，则显式创建指定管理员。
遇到身份已绑定其他账号、目标账号停用或不是管理员时拒绝操作，不自动合并。

迁移删除密码字段，不支持自动降级恢复密码。其他未绑定的历史账号保留数据，
无法再通过旧密码或 JWT 登录。发布时同步更新前后端和 Worker。

### 登录态和错误处理

`get_current_user` 统一读取 Redis Session，调用 `/internal/token/verify`，
核对本地身份、停用和删除状态。每个请求内使用 FastAPI 依赖缓存避免重复验证。

登录时直接使用兑换结果中的用户信息和 `expires_in` 创建会话，不立即重复调用验证接口。
从兑换开始时间计算会话到期时间，创建时扣除已耗时；当前测试环境返回的有效期为 24 小时。首版不使用
refresh token，不自动续期。退出先删除本地 Session、清除 Cookie，再请求统一退出。
上游退出失败仅记录脱敏日志，本地退出仍然生效。

未登录、本地会话过期或身份不匹配返回 401；本地停用返回 403。
上游响应只判断 `code == 0`，非零业务码、请求失败或响应格式错误统一返回 503，
不再区分上游撤销、停用和服务故障，也不因此清除当前 Cookie。Redis 故障同样返回 503。
Cookie 写请求校验固定的 APP_ORIGIN；MCP API Key 鉴权独立保留。

### 当前协议限制

现有 Auth Server 未确认支持将 ticket 与业务端发起登录的浏览器绑定；实测自定义
state/nonce 未被透传。当前实现按已公布接口兑换 ticket，没有虚构关联参数，
Origin 校验不等价于登录请求绑定。登录 CSRF 防护仍需 Auth Server 协议补齐后联调，
不能将当前实现视为已解决该问题。ticket 的平台隔离语义同样尚未明确。
