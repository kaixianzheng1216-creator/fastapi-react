# 知识库功能实施计划

本文定义多知识库首版的业务边界、技术方案和实施顺序。管理员维护知识库和文档，用户按会话选择知识库，Agent 只在当前会话的有效范围内检索并引用来源。

## 首版范围

首版完成以下闭环：

- 管理员创建、编辑、启停和删除多个知识库
- 管理员上传文档并查看处理状态、失败原因和 Markdown 预览
- 管理员测试知识库检索结果
- 用户按会话选择多个已开放知识库
- Agent 按需检索所选知识库并引用来源

以下能力没有首版验收场景：

- 知识库目录和文件夹层级
- 文档在线编辑、批注和版本管理
- Chunk 管理和人工编辑
- BM25、RRF、Rerank 和父子检索
- 多 Embedding 模型同时运行和在线索引切换
- 自动重试、任务优先级和分布式任务系统
- 每个知识库独立使用 Qdrant Collection
- MinerU 和多解析器切换

## 技术方案

首版沿用现有 FastAPI 单体应用，增加一个独立 Worker，不拆微服务或建设通用 RAG 框架。

```text
管理后台
  ↓
知识库与文档 API
  ↓
PostgreSQL + COS
  ↓
Knowledge Worker
  ↓
Docling → HybridChunker → LiteLLM Embedding
  ↓
Qdrant
  ↓
用户按会话选择知识库
  ↓
Agent search_knowledge 工具
```

各存储只承担一种主要职责：

| 存储 | 保存内容 | 定位 |
| --- | --- | --- |
| PostgreSQL | 知识库、文档状态和会话关系 | 业务事实与权限边界 |
| 腾讯云 COS | 原文件、DoclingDocument JSON 和 Markdown | 文件事实与可重建产物 |
| Qdrant | Chunk、向量和检索元数据 | 可重建的检索索引 |

Qdrant 数据丢失时，可以使用 PostgreSQL 中的文档记录和 COS 中的 DoclingDocument JSON 重建。检索权限始终由 PostgreSQL 决定，Qdrant 和 COS 不作为授权依据。

### 运行依赖

第二阶段增加以下依赖和服务：

- Backend 增加 Qdrant 客户端
- Backend 增加 `docling-core[chunking]` 和 BGE-M3 tokenizer 依赖
- LiteLLM 接入 Cloudflare Workers AI 的 `@cf/baai/bge-m3`
- Compose 增加带持久化卷的 Qdrant 服务
- Compose 增加使用 Backend 镜像的 Worker 服务

首版固定使用 Cloudflare Workers AI 托管的 `@cf/baai/bge-m3`、`BAAI/bge-m3` tokenizer 和 1,024 维向量。Collection 默认命名为 `knowledge_chunks_v1`。配置方式见 [Cloudflare Workers AI Key 获取指南](<./Cloudflare Workers AI Key 获取指南.md>)。

Worker 启动时创建缺失的 Collection 和 Payload Index。已有 Collection 的向量维度不匹配时启动失败。Collection 存在 Point 后，不允许原地更换 Embedding 模型或 tokenizer；相同维度不代表相同向量空间。后续更换模型时创建新版本 Collection，并从 DoclingDocument JSON 重建。

## 业务规则

### 文件类型

聊天附件和知识库尽量共用文件类型，差异只来自处理能力：

| 类型 | 聊天附件 | 知识库 |
| --- | --- | --- |
| PDF、DOCX、PPTX、XLSX、HTML、Markdown、TXT、CSV、JSON | 支持 | 支持 |
| JPEG、PNG、GIF、WebP | 支持 | 不支持 |

两条链路共用文件类型和 100 MB 原文件上限，按处理方式设置其他限制：

| 限制 | 聊天附件 | 知识库 |
| --- | --- | --- |
| 单次选择数量 | 每条消息最多 9 个 | 不设批量上传入口 |
| 文本附件大小 | Markdown、TXT、CSV、JSON 单文件最大 256 KB | 不单独限制 |
| 提取文本大小 | 每条消息的非图片附件合计最大 256 KB | 不限制 |
| 分页文档页数 | 不单独限制 | 最多 1,000 页 |
| Docling 单次解析时间 | 沿用同步解析超时 | 最多 30 分钟 |

图片在聊天中可以直接交给多模态模型，但进入知识库还需要定义 OCR 质量和图片引用，因此首版只有图片不进入知识库。

### 知识库开放状态

`is_enabled` 表示知识库是否向普通用户开放：

- 新建知识库默认停用
- 管理员可以查看和维护所有知识库
- 普通用户只能看到已启用且包含 `ready` 文档的知识库
- 停用后立即禁止用户选择和检索
- 停用不删除文档、索引和历史会话关系

### 文档处理状态

```text
pending → processing → ready
                    ↘ failed
                    ↘ timed_out

failed ─────人工重试──→ pending
timed_out ──人工重试──→ pending
```

- `pending`：等待 Worker 领取
- `processing`：正在解析或索引
- `ready`：可以预览和检索
- `failed`：处理失败，可以人工重试
- `timed_out`：处理超过 30 分钟，可以人工重试

### 会话选择

- 一个会话可以选择多个知识库
- 新会话默认不选择知识库
- 选择结果随会话持久化
- 每次 Tool 调用都重新校验会话所有权和知识库状态
- 未选择有效知识库时不访问 Embedding 和 Qdrant

## 数据模型

首版只新增三张 PostgreSQL 表。Chunk 正文不写入 PostgreSQL。

### knowledge_base

```text
id              UUID, primary key
name            varchar(100), unique, not null
description     varchar(500), nullable
is_enabled      boolean, not null, default false
created_at      timestamptz, not null
updated_at      timestamptz, not null
```

### knowledge_document

```text
id                       UUID, primary key
knowledge_base_id        UUID, foreign key, cascade delete
stored_file_id           UUID, unique, foreign key
status                   varchar, not null
error_message            text, nullable
processing_started_at    timestamptz, nullable
created_at               timestamptz, not null
updated_at               timestamptz, not null
```

字段约束如下：

- `status` 只允许 `pending`、`processing`、`ready`、`failed` 和 `timed_out`
- `error_message` 只保存适合后台展示的失败或超时摘要，完整异常写入服务日志
- `stored_file_id` 唯一，一个原文件只能属于一个知识库文档

为文档列表和 Worker 领取任务建立两个索引：

```text
knowledge_document(knowledge_base_id, created_at)
knowledge_document(status, created_at)
```

解析产物使用固定对象路径，无需在数据库重复保存：

```text
knowledge/{document_id}/document.json
knowledge/{document_id}/preview.md
```

### conversation_knowledge_base

```text
conversation_id      UUID, foreign key, cascade delete
knowledge_base_id    UUID, foreign key, cascade delete
primary key          conversation_id + knowledge_base_id
```

联合主键支持按会话读取完整选择结果。另为 `knowledge_base_id` 建索引，支持删除知识库时清理关系。

### Qdrant Point

所有知识库共用 `knowledge_chunks_v1`：

```text
id: chunk_id

vector:
  dense

payload:
  knowledge_base_id
  document_id
  filename
  content
  section_path
  page_numbers
```

`content` 保存原始 `chunk.text`，用于回答和引用。`filename` 随检索结果返回，避免逐条查询 PostgreSQL。

`knowledge_base_id` 和 `document_id` 使用 Keyword Payload Index。`knowledge_base_id` 设置 `is_tenant=true`，用于共享 Collection 下的数据分区。

`chunk_id` 使用 UUIDv5，以 `document_id` 为 namespace、分块序号为 name。同一文档按相同顺序切片时生成相同 ID。

## 文档处理链路

知识库复用现有 `StoredFile`、COS 直传和公共上传校验。由于聊天附件需要立即形成消息上下文，而知识库需要异步索引，知识库保留独立的上传完成逻辑和 Docling 客户端。

### 上传

知识库接受“文件类型”一节定义的公共文档类型和大小限制。

```text
创建 StoredFile 和 knowledge_document
  ↓
浏览器直传 COS
  ↓
完成接口校验对象、大小和实际类型
  ↓
将 StoredFile 标记为 uploaded
```

`knowledge_document` 创建时为 `pending`，但 Worker 只领取关联 `StoredFile.uploaded = true` 的记录。完成接口不调用 Docling。上传校验失败时删除无效文件和文档记录；Worker 解析失败时保留原文件，以便人工重试。

### 解析与索引

Worker 使用 PostgreSQL 的 `FOR UPDATE SKIP LOCKED` 领取已完成上传的 `pending` 文档。知识库使用独立的 Docling 客户端，不扩展聊天附件的同步解析函数。

PDF、Office、HTML、Markdown、TXT 和 CSV 使用 Docling 解析。JSON 必须是 UTF-8 编码的合法 JSON，Worker 将原文转换为 DoclingDocument 文本结构。两条路径最终都生成 DoclingDocument JSON 和 Markdown，并共用后续切片与索引流程。

知识库不限制解析后 Markdown 的字节数和单文档 Chunk 总数。原文件限制为 100 MB、1,000 页，单次 Docling 调用最多 30 分钟。

```text
下载原文件
  ↓
生成 DoclingDocument JSON 和 Markdown
  ↓
保存解析产物到 COS
  ↓
HybridChunker 切片
  ↓
LiteLLM 生成 Embedding
  ↓
批量写入 Qdrant
  ↓
文档进入 ready
```

Docling 保留 OCR 和表格解析，不启用图片描述。HybridChunker 使用与 Embedding 模型匹配的 tokenizer：

- `chunker.contextualize(chunk)` 用于生成 Embedding
- `chunk.text` 写入 Qdrant Payload，供 Agent 回答
- 标题路径和页码写入独立 Payload 字段

Worker 每次处理前按 `document_id` 删除旧 Point。删除和 Upsert 都使用 `wait=true`，Upsert 每批固定为 64 个 Point。

全部批次完成后，Worker 才将文档设置为 `ready`。没有生成有效 Chunk 或任一步骤失败时，Worker 删除该文档的 Point，将状态更新为 `failed`，并写入 `error_message`。处理超过 30 分钟时执行相同清理，将状态更新为 `timed_out`。

人工重试将 `failed` 或 `timed_out` 文档重新置为 `pending` 并清空旧错误。Worker 优先读取已有 DoclingDocument JSON 解析产物，解析产物不存在时才重新处理原文件。

首版只运行一个 Worker 实例。Worker 启动时将处理超过 30 分钟的 `processing` 文档更新为 `timed_out`，并删除该文档的 Point。首版不实现定时扫描或自动重试。

### 重建索引

提供一个内部命令，将指定知识库或全部 `ready` 文档重新置为 `pending`。Worker 使用 COS 中的 DoclingDocument JSON 重建索引。首版不提供重建页面。

## 检索与 Agent

后台检索测试和 Agent Tool 共用同一个 Retrieval Service，避免形成两套检索规则。

### 检索范围

每次检索执行以下步骤：

1. 从 PostgreSQL 读取当前允许使用的知识库
2. 查询这些知识库中的 `ready` 文档 ID
3. 为问题生成 Embedding
4. 使用 Qdrant `MatchAny` 过滤知识库 ID 和文档 ID
5. 执行 Cosine Dense Top 6

检索结果包含知识库名称、文件名、原始片段、标题路径、可选页码和相似度分数。即使 Qdrant 存在残留 Point，非 `ready` 或已删除文档也不能进入结果。

### Agent Tool

Agent 增加一个工具：

```text
search_knowledge(query: str)
```

聊天请求将 `user_id` 和 `conversation_id` 写入 Agent Runtime Context。Tool 每次调用都根据这两个值重新校验会话所有权、会话选择、知识库状态和文档状态。

Tool 不接收用户 ID、知识库 ID、`top_k` 或索引参数。前端和 Agent 都不能扩大后端确定的检索范围。没有有效知识库时，Tool 直接返回空结果。

检索片段是不可信参考资料，不是系统指令。Agent 必须忽略片段中要求改变规则、调用工具或泄露信息的指令。

Agent 按可用元数据引用来源：

```text
[来源：品牌手册.pdf，第 12 页]
[来源：品牌规范.md，视觉规范]
[来源：品牌规范.md]
```

## 删除与外部资源清理

删除操作先切断业务访问，再清理外部资源：

1. 保存待清理的 COS 对象路径和文档 ID
2. 删除 PostgreSQL 记录并提交
3. 按文档 ID 删除 Qdrant Point
4. 删除原文件、DoclingDocument JSON 和 Markdown

删除知识库时，对其文档执行相同清理。外部资源清理失败时写入服务日志，不恢复数据库记录。此时允许存在不可访问的残留对象，业务数据不能被继续检索。

## 分阶段实施

三个阶段全部属于首版，按顺序开发和验收。

### 第一阶段：后台知识库管理

第一阶段交付知识库实体、管理接口和后台列表。

新增 `app/modules/knowledge`，沿用现有模块结构：

```text
knowledge/
├── exceptions.py
├── models.py
├── router.py
├── schemas.py
└── service.py
```

管理接口：

```text
POST   /api/v1/admin/knowledge-bases
GET    /api/v1/admin/knowledge-bases
GET    /api/v1/admin/knowledge-bases/{knowledge_base_id}
PATCH  /api/v1/admin/knowledge-bases/{knowledge_base_id}
DELETE /api/v1/admin/knowledge-bases/{knowledge_base_id}
```

所有接口复用 `get_current_active_superuser`。列表支持分页、名称搜索和状态筛选。名称去除首尾空格，不能为空或重复；名称最长 100 个字符，描述最长 500 个字符。名称重复返回 409，记录不存在返回 404。

后台侧栏增加“知识库”，路由为 `/admin/knowledge-bases`。列表展示名称、描述、状态、创建时间和操作，支持创建、编辑、启停、删除、搜索、筛选和分页。

前端复用用户管理页面的 Table、Dialog、DropdownMenu、AlertDialog、Pagination 和 React Query 写法。

验收条件：

- 管理员可以创建、编辑、启停和删除多个知识库
- 新知识库默认停用
- 普通用户不能调用管理接口
- 页面交互与现有管理后台一致

### 第二阶段：文档处理与后台检索

第二阶段交付文档上传、Worker、Markdown 预览和检索测试。

Backend 统一定义公共文档白名单、聊天专属白名单和场景限制。Frontend 使用相同的 MIME 列表，其中 Markdown 接受 `text/markdown` 和常见的 `text/plain`。

管理接口：

```text
POST   /api/v1/admin/knowledge-bases/{knowledge_base_id}/documents/uploads
POST   /api/v1/admin/knowledge-documents/{document_id}/complete
GET    /api/v1/admin/knowledge-bases/{knowledge_base_id}/documents
GET    /api/v1/admin/knowledge-documents/{document_id}/preview
DELETE /api/v1/admin/knowledge-documents/{document_id}
POST   /api/v1/admin/knowledge-documents/{document_id}/retry
POST   /api/v1/admin/knowledge-bases/{knowledge_base_id}/search
```

知识库详情路由为 `/admin/knowledge-bases/{knowledge_base_id}`。页面包含上传、文档列表、处理状态、失败原因、人工重试、删除、Markdown 预览和检索测试。

预览接口返回只读 Markdown：

```json
{
  "content": "# 文档标题\n\n文档正文"
}
```

前端复用现有 Markdown 渲染组件，不提供编辑、批注和版本对比。

验收条件：

- 知识库支持文件类型表中定义的全部公共文档类型
- 上传接口不等待 Docling
- 文档可以进入 `ready`、`failed` 或 `timed_out`
- 解析失败后原文件仍可用于重试
- 重复处理不会产生重复或残留 Point
- Worker 重启不会让任务永久停留在 `processing`
- 超过 100 MB 或 1,000 页的文档处理失败，Docling 单次调用超过 30 分钟时进入 `timed_out`
- 管理员可以查看 Markdown 预览并测试 Dense 检索
- 检索结果包含文件名，以及可用的标题路径或页码
- 删除后不能再检索相关文档

### 第三阶段：用户选择与 Agent 检索

第三阶段交付会话知识库选择器和 `search_knowledge` Tool。

用户接口：

```text
GET /api/v1/knowledge-bases
GET /api/v1/agent/conversations/{conversation_id}/knowledge-bases
PUT /api/v1/agent/conversations/{conversation_id}/knowledge-bases
```

`PUT` 一次提交完整选择结果。后端校验会话所有权和知识库状态。消息输入框附近增加知识库多选器，恢复历史会话时同步恢复选择。

验收条件：

- 用户只能看到已启用且包含 `ready` 文档的知识库
- 一个会话可以选择多个知识库
- 刷新页面后选择保持不变
- 未选择知识库时不访问 Embedding 和 Qdrant
- Agent 只能检索当前会话的有效知识库
- 停用知识库后立即禁止检索
- 伪造知识库 ID 不能扩大检索范围
- 回答包含可追溯的来源信息

## 验证要求

每个阶段完成后执行：

1. 创建对应 Alembic 迁移
2. 重新生成前端 API 客户端
3. 运行 Ruff 和 Mypy
4. 运行前端 TypeScript 检查和生产构建
5. 验证本阶段接口、权限和页面交互

自动化测试覆盖以下关键路径：

- 管理员权限、知识库启停和会话所有权
- 文件白名单和异步上传完成流程
- 知识库原文件大小、页数和处理超时
- 解析失败后保留原文件
- 文档状态转换、重复处理和 Worker 超时识别
- Qdrant 写入完成后才将文档设置为 `ready`
- 失败、超时、重试和删除后不存在可检索的数据
- Embedding 模型或 tokenizer 变化时不能复用现有 Collection
- Tool 每次调用重新校验知识库状态
- 有页码和无页码文档的来源引用

首版上线前使用代表性问题验证正确片段能否进入 Top 6。只有评测或生产数据确认问题后，才增加 BM25、RRF、Rerank 或其他检索策略。

第一、二阶段构成后台知识库闭环。第三阶段完成用户选择、Agent 检索和来源引用，交付完整首版。
